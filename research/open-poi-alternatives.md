# Open/free POI enrichment alternatives for TREK

Research date: 2026-09-18. Sources are provider documentation, project documentation, or first-party licenses. Quotas and commercial terms can change, so production integration should pin the accepted terms and monitor the provider dashboard.

## Recommendation

Use a two-tier, provider-neutral enrichment model:

1. **Categories and stable identity:** make **Foursquare Open Source Places (FSQ OS Places)** the first candidate for a locally stored POI index. It is global, commercially usable under Apache 2.0, exposes stable `fsq_place_id` values and a six-level category taxonomy, and is delivered as queryable Iceberg/Parquet data with deltas. Its open schema contains no photo field. Preserve Foursquare's `NOTICE.txt`. [schema](https://docs.foursquare.com/data-products/docs/places-os-data-schema), [access](https://docs.foursquare.com/data-products/docs/access-fsq-os-places), [license notice](https://opensource.foursquare.com/places-notice-txt/)
2. **Low-operations pilot:** if importing/indexing FSQ data is too much for the first release, use **Geoapify Places/Place Details** behind TREK's server. Its free plan currently provides 3,000 credits/day and up to 5 requests/second, permits commercial use and stored results, and provides stable place IDs, hierarchical categories, and occasional `wiki_and_media.image` URLs. Free use requires Geoapify and OpenStreetMap attribution. [Places API](https://apidocs.geoapify.com/docs/places/), [Place Details](https://apidocs.geoapify.com/docs/place-details/), [pricing](https://www.geoapify.com/pricing/), [terms](https://www.geoapify.com/terms-and-conditions/)
3. **Photos:** treat photos as a separate, optional enrichment. Match high-confidence POIs to **Wikidata QIDs**, obtain `P18`, then retrieve the Commons file's license, author, attribution text, and canonical page URL. Store those fields with the thumbnail URL. Wikidata structured data is CC0, but each Commons file has its own license and may require attribution/share-alike. Coverage is strongest for notable sights, not ordinary restaurants. [Wikidata reuse](https://www.wikidata.org/wiki/Wikidata:Reuse), [P18](https://www.wikidata.org/wiki/Help:Frequently_used_properties/en), [Commons reuse](https://commons.wikimedia.org/wiki/Commons:Simple_media_reuse_guide)
4. Keep the existing Google Place ID as an external identifier only. Never blend Google-returned attributes into the open POI record unless Google's terms explicitly permit that field and retention.

This combination removes most recurring category calls, allows lawful persistent caching, and avoids depending on a fragile public OSM endpoint. It cannot promise a photo for every place. No open source evaluated here matches Google Places' user-photo breadth.

## Viewport-only enrichment architecture

### Stored model

Persist one canonical TREK place row plus provider links:

```text
place
  trek_place_id
  name, lat, lon, city
  google_place_id?                 # identifier only
  fsq_place_id? / overture_gers_id? / geoapify_place_id? / wikidata_qid?
  category_key?, category_label?, category_source?, category_source_version?
  photo_url?, photo_page_url?, photo_author?, photo_license?, photo_attribution?
  match_confidence?, enriched_at?, refresh_after?, failure_count?
```

Never silently merge fields from different providers. Record provenance per field and keep source-required notices/attributions renderable.

### Request flow

1. Render the itinerary immediately from TREK data, with a deterministic placeholder for missing category/photo.
2. A browser `IntersectionObserver` marks a card eligible only after it enters a small prefetch margin. The browser sends TREK IDs, not provider credentials, to one server endpoint.
3. The server checks persistent enrichment first. It single-flights identical misses, deduplicates IDs, and places unresolved work in a bounded queue. Return cached/stale data immediately where safe.
4. Resolve categories locally from FSQ OS Places or Overture by stored provider ID. For legacy Google-only rows, do a one-time high-confidence name + coordinate + city match; require a close distance and normalized-name threshold, otherwise leave unknown rather than mislabel.
5. Resolve photo metadata only when the now-visible card still lacks a photo. Batch Wikidata entity reads, then fetch Commons metadata for the selected `P18`. Persist URL plus complete attribution/license metadata. Do not hotlink an unlicensed arbitrary website image.
6. Use short negative-cache entries so missing photos are not retried on every scroll. Refresh open category data on dataset releases; refresh photo metadata much less often, while tolerating deletion or license changes.

### Rate-limit behavior

- Maintain separate server-side token buckets per provider and per API key. Start below documented limits: Geoapify at 4 RPS, Wikimedia at 2 concurrent/120 requests per minute, and public Nominatim at 1 serial request per second only for deliberate low-volume fallback.
- Limit each browser to one enrichment request in flight and cap each payload, for example 20 TREK place IDs. That is an application batch; the server may translate it into provider-supported batches or serial calls.
- Honor `429` and `Retry-After`; otherwise use exponential backoff with jitter. Do not retry other 4xx responses. Apply a circuit breaker after repeated provider failures.
- Cancel work for cards that leave view before dispatch. Once dispatched, finish and cache useful work rather than issuing another call later.
- Add daily budget ceilings and metrics for cache hit rate, provider calls, 429s, match confidence, and photo attribution completeness. A quota exhaustion must degrade to labels/placeholders, never break the itinerary.

## Decision

For TREK now, the safest implementation is **FSQ OS Places locally for categories + Wikidata/Commons for optional photos**, with **Geoapify as the fastest hosted pilot/fallback**. Do not use the public Nominatim or Overpass instances as production enrichment backends. Do not select HERE or TomTom for a persistent database cache. Keep Google's Place ID for interoperability while eliminating routine Google detail requests.
